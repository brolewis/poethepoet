# Shell Completions Spec (Issue 55)

Issue reference:
```
https://github.com/nat-n/poethepoet/issues/55
```

## Scope

Define required behavior for bash and zsh completion scripts generated by
`poe _bash_completion` and `poe _zsh_completion`, plus the builtin helpers they
call. Fish is out of scope.

## Poe CLI fundementals

- General form: `poe [global options] task [task arguments] -- [extra arguments]`.
- Global options must appear before the task name.
- The first non-option token is treated as the task name.
- `--` ends Poe's own parsing; everything after is forwarded as extra arguments.
- `-C/--directory/--root` selects the project/config root; if repeated, the last one wins.
- Task arguments (options and positionals) come from the task's `args` definition.
- Hidden tasks (names starting with `_`) are not user-facing.
- the `--root` global option is deprecated, as indicated by the fact that it has help set to argparse.SUPPRESS, so should not be offered as a completion

## Requirements

1) Compatibility
   - Backward compatibility is required only for `_list_tasks` and
     `_describe_tasks` outputs (older completion scripts may rely on them).
   - `_describe_tasks` output format matches `_list_tasks`: space-separated task
     names in config order.

2) Global options
   - Global options must be hard coded in the generated script via a single source
     of truth derived from the argparse parser.
   - Executor option values are the only explicit exception to the parser-derived
     global option source.
   - `-e/--executor` completion should be hard-coded to:
     `poetry`, `simple`, `uv`, `virtualenv`, `auto`.
   - `-X/--executor-opt` but we don't know what it is, so for the purpose of completion we treat this option as if it didn't accept a value.

3) Performance
   - Builtin completion helpers should import as few module as possible.
   - Shell scripts should make the minimum number of calls to python per completion invocation.
   - python completion helpers must fail gracefully without raising errors, for example if no config exists

4) Testability
   - Completion-related Python code should be decomposed into pure, testable functions where appropriate.
   - Unit tests should be complete and well organized.
   - Shell script contracts should be testable from Python by generating or exposing discrete script functions when feasible.

5) Shared behavior (bash + zsh)
   - Hidden tasks (names starting with `_`) are never suggested.
   - `-C` and `--directory` accept a path; when present without a value, completion must suggest paths and return early.
   - Both short and long options are suggested as appropriate.
   - Do not suggest an option already present unless it is configured with
     `multiple = true` or `multiple = N` where `N` is greater than the number of times it has already been supplied.
   - Task option repeatability metadata must be available in helper outputs (see Builtin output contracts) to make the above enforceable.
   - Counting rules for repeated options:
     - Short and long forms of the same option count as the same logical option.
     - For `multiple = N`, stop suggesting once total uses across all aliases reaches `N`.
   - If `-C PATH` / `--directory PATH` is provided, completions must be generated from the referenced project.
   - If multiple `-C`/`--directory` are provided, the last one wins.
   - Choices containing spaces must be suggested correctly for each shell (appropriate quoting/escaping for bash and zsh).

6) Completion flow
   - If no task is provided, suggest global options or task names.
   - If completing the value position immediately after the `--help` global option, then suggest task names as the optional value, and also suggest other global options.
   - Do not suggest global options or task names after the task name (task args or fallback path completion only).
   - Suggest the most appropriate value for global or task options:
     - choices when defined
     - paths when a path is expected
   - After `--`, fall back to path completion for extra arguments.

7) Positional arguments
   - When not completing a value for an option, the baseline behavior is:
     - if the current word starts with `-`, suggest options
     - otherwise suggest file paths
   - If the current position corresponds to a positional argument with choices, suggest those choices instead of file paths.
   - Positional arguments are completed in declaration order; only the last
     positional may accept multiple values.
   - If the last positional allows multiple values, continue suggesting values
     for that same positional until the allowed count is reached (or indefinitely
     if `multiple = true`).

## Design notes (zsh focus)

- Prefer a small, explicit state machine in the zsh script to decide a single
  Python call per completion invocation:
  - no task yet -> `_zsh_describe_tasks`
  - task selected -> `_zsh_task_args`
  - after `--` -> file completion only
- Keep shell logic modular by factoring completion paths into local zsh
  functions (task list, args list, option value handling), enabling targeted
  harness tests.
- Use lightweight in-shell caching to avoid repeated calls within a session:
  - cache task descriptions keyed by `target_path`
  - cache task args keyed by `target_path|task`
  - consider the cache stale after 1 hour

## Design notes (bash focus)

- Bash completion uses `COMP_WORDS`/`COMP_CWORD`; implement a small state machine
  to decide a single Python call per path when possible:
  - no task yet -> `_list_tasks`
  - option value completion -> `_bash_task_arg_choices`
  - option completion after task -> `_bash_task_args`
  - after `--` -> file completion only
- Bash 3.2 (macOS default) lacks associative arrays; keep caching minimal:
  - at most cache the last `target_path` and last `task` result string
  - no multi-key caches or complex invalidation
- The boolean‑option path may require two calls (`_bash_task_arg_choices` then
  `_bash_task_args`), which is acceptable.

## Tests

- All behaviors above should be covered with tests where practical without
  adding heavy dependencies beyond standard bash/zsh or common Python packages.
- Prefer a hybrid strategy:
  - Pure Python unit tests for completion models and renderers.
  - Targeted shell harness tests that generate a single function and run it
    under bash/zsh with minimal stubs, validating the contract (for example
    `_arguments`/`_describe` inputs in zsh or `COMPREPLY` in bash).
